# 디자인: 식품안전나라 레시피 CSV 카탈로그

## 설계 원칙

- 대상은 `apps-in-toss.config.ts`의 `ait-fridgepick` 앱인토스 WebView 미니앱이다.
- CSV는 앱 개발·데이터 갱신 때 운영자가 공식 경로에서 수동으로 받는다.
- 앱 실행 중 원격 통신은 하지 않으며, 인증키가 AIT WebView 클라이언트와 앱 번들에 필요하지 않은 구조를 유지한다.
- 데이터는 Vite 웹 번들과 AIT 번들 안에서 사용할 수 있는 작은 정적 카탈로그로 제공한다. 번들 크기와 실행 환경에서의 로딩 결과를 확인한다.
- 원본 파일은 로컬 전용 입력으로 취급한다. 정제된 데이터도 이용 조건이 확인되기 전에는 저장소에 추가하지 않는다.
- 기존 `Recipe` 타입과 재료 ID를 우선 사용해 변경 범위를 제한한다.
- 원본 문구를 완전히 해석하지 못한 레코드는 필수 재료를 임의로 누락해 추천하지 않는다.

## 수집·정규화 흐름

1. 사용자가 인증키를 공식 식품안전나라 절차에서 사용해 CSV를 받는다. 인증키는 Codex 대화에 붙여넣거나 코드·환경 변수·로그에 저장하지 않는다.
2. 원본 CSV를 저장소 밖 또는 Git에서 제외한 로컬 입력 경로에 둔다. 원본 파일은 커밋하지 않는다.
3. CSV 인코딩·헤더·레코드 수·고유 원본 ID·필수 열을 검사한다. 파싱 오류는 임의 복구하지 않고 건수와 행 식별 정보를 기록한다.
4. 원본 재료 정보에서 조리 전제나 양을 제외하고 식재료 표현을 추출한다. 구체적인 필드 파싱 규칙은 CSV 샘플을 확인한 뒤 계획에서 확정한다.
5. 명시적 별칭 사전을 사용해 재료를 기존 카탈로그 ID로 매핑한다. 문자열 유사도만으로 새 ID를 추측하지 않는다.
6. 필수 재료가 불완전하게 매핑되거나 절차·제목 등 필수 내용이 유효하지 않은 행은 앱 데이터에서 제외하고 사유를 집계한다. 선택 재료 정보의 손실도 기록한다.
7. 출처의 재사용 조건이 앱 내 정적 제공과 변환을 허용한다고 확인된 경우에만 정규화 데이터를 생성하고, 출처·원본 ID·확인된 라이선스 정보를 보존한다.
8. 기존 20개 레시피를 유지한 채 중복 여부, 추천 후보, 선택 재료 대표 사례를 검증한다.

## 데이터 모델과 식별자

- 기존 `Recipe` 계약을 유지한다: `id`, `name`, `requiredIngredients`, 선택적인 `optionalIngredients`, `steps`, `difficulty`.
- 앱 내부 ID는 원본의 안정적인 레코드 식별자를 사용해 기존 ID와 충돌하지 않도록 접두어를 둔다. 구체적인 문자열은 실제 CSV ID를 확인한 뒤 계획에서 확정한다.
- 정규화된 재료 배열에는 현재 `src/data/ingredients.ts`에 있는 ID만 둔다.
- 출처 필드가 현재 타입에 없으므로, 추적성과 화면 출처 표시를 위해 필요한 최소 타입 변경을 구현 계획에서 정한다. 원본 전체 CSV 행을 타입 안에 복사하지 않는다.
- 원본에서 얻은 조리문·이미지·영양정보는 이용 권한과 제품상 필요가 확인된 경우에만 포함한다. 필요하지 않은 원본 필드는 복사하지 않는다.

## 보안·배포 제약

- 인증키를 `VITE_*` 환경 변수로 두지 않는다. Vite 클라이언트 변수는 브라우저 번들에 노출될 수 있다.
- 식품안전나라 상세 페이지가 안내하는 파일 URL에는 인증키가 경로에 들어가며 HTTP 주소로 표기되어 있다. 전송 보호가 확인되지 않은 직접 URL 자동 호출은 사용하지 않는다.
- 실제 CSV 취득은 공식 포털의 로그인·다운로드 절차를 사용한다. 다운로드 동작이 안전한 전송으로 제공되는지 확인할 수 없으면 키가 포함된 요청을 진행하지 않고 사용자에게 확인 결과를 알린다.
- 원본 CSV는 외부 작업 로그, 오류 로그, 캡처, 커밋에 첨부하지 않는다.
- 제공기관의 데이터 조건이 불명확하면 앱에서 사용할 레시피 텍스트를 생성·배포하지 않는다.

## 정규화 정책

- 메뉴명·단계 문구는 공백 등 명백한 형식 문제만 정리하고 의미를 재작성하지 않는다.
- 별칭은 확인된 한국어 표현을 명시적으로 등록하고, 변경 이유를 기록한다.
- 한 레시피의 재료가 기존 카탈로그 ID로 모두 신뢰성 있게 표현되지 않으면 포함 대상에서 제외한다. 미확인 원재료를 조용히 버리지 않는다.
- 같은 원본 ID 중복, 유효하지 않은 조리 단계, 필수 재료 부족, 재료 매핑 누락을 각각 별도 사유로 집계한다.
- 소스 DB의 포함 수, 처리 수, 제외 수와 원인은 로컬 생성 요약에 남기되, 인증정보와 원본 전체 텍스트는 기록하지 않는다.
- 최소 포함 레코드 수와 구체적인 매핑 규칙은 CSV 실제 분포를 본 후 합의한다.

## 앱 동작

- 기존 60% 필수 재료 매칭 임계값과 후보 무작위 선택 흐름을 우선 유지한다.
- CSV 데이터 전후로 동일한 대표 재료 선택 묶음을 사용해 후보 없음 비율, 후보 개수를 비교한다.
- 추천 결과에서 필요한 재료는 기존 재료 이름 조회 규칙으로 표시할 수 있어야 한다.
- 재료 ID 또는 결과 화면 모델을 바꿔야만 출처의 필수 재료를 안전하게 나타낼 수 있다면 구현 전에 그 변경 범위를 계획과 함께 검토한다.
- `npm run build`가 수행하는 TypeScript 검사, Vite 번들 생성, `ait build`를 확인한다. AIT DevTools의 320×640 CSS px 미리보기에서 긴 레시피명, 조리 단계, 출처 문구가 잘리지 않고 필요한 세로 스크롤이 동작하는지 확인한다.
- AIT DevTools 검증과 실제 Toss 테스트 환경 검증은 구분해 기록한다. 환경을 이용할 수 없으면 해당 검증을 완료로 표시하지 않는다.

## 미확정 사항

- CSV 실제 인코딩, 헤더, 레코드 수, 현재 DB 업데이트 시점
- 재료 정보에서 필수·선택 항목을 식별하는 일관된 방법
- 전체 레시피 본문·이미지의 재배포와 가공 허용 조건
- 별칭 보강 또는 재료 선택 카탈로그 확장이 필요한 규모
- 앱 번들 크기에 대한 영향과 포함 가능한 데이터 상한
- 현재 AIT 번들 업로드 한도와 제출 시점의 검토 조건
