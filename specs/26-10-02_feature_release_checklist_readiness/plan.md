# 실행 계획: 비게임 출시 검증

## 기준과 이번 범위

로드맵11단계의 로컬 구현은3a9972c·c4f44f7에 있다. 다음 미완료 범위는 11단계 실기기 확인과12단계 출시 전 검증이다. 기존 같은 목적의 명세를 재사용하며 문서 브랜치 feature/release-validation-specs는 c4f44f7에서 분기했다. 이 문서 정리는 기능 구현·기기 검증·업로드·출시를 수행하지 않는다.

[requirements.md](./requirements.md)의 RCR-01~14가 완료 기준이다. 실제 결과는 [validation.md](./validation.md)에만 증거와 함께 기록한다. 상태 구현은 [USP 계획](../26-10-04_feature_user_state_persistence/plan.md), 광고 구현은 [IB 계획](../26-10-04_feature_ingredient_banner/plan.md)을 따른다.

## 선행 조건

- 대상 번들의 소스SHA·빌드 모드·번들 ID를 고정한다. 현재 원격 구현 HEAD는 c4f44f7이다.
- Node24.15 이상/잠금 의존성을 확인한다. 이전 실행 환경은24.19.0이다.
- 테스트 번들은 기본 build로 생성하며 release 산출물은 QR 테스트에 사용하지 않는다. 두 모드가 같은 ait-fridgepick.ait 이름을 덮어쓰므로 모드와 생성 시점을 혼동하지 않는다.
- 테스트 산출물의 실제 광고 ID 부재를 값 비노출 방식으로 확인한다. 분기 테스트 통과만으로 최종 파일 검사 완료를 대신하지 않는다.
- 대상 OS/토스 버전·실기기·테스트 진입 권한을 확보한다. 브라우저 mock/콘솔 isTested=true를 기기 QA 증거로 대체하지 않는다.
- 약관 수락·검수 제출·라이브 전환·이력 재작성은 이번 문서 준비 범위 밖이다. 후속 실행 때 해당 동작의 사용자 지시·권한을 확인한다.

## 다음 기기 실행 순서

1. 번들 준비/ID 검사와 대상 기기 정보를 validation에 기록한다.
2. 앱 진입→재료 김치/밥 선택→매칭률65%·쉬움→추천을 수행한다. API HASH는 타입/지원 여부만 기록하고 실제 값은 남기지 않는다.
3. 저장 완료 후 앱 완전 종료·재진입: 홈부터 시작하며 재료2개/65%/쉬움을 확인한다. 처음부터 이후 재진입은0개/60%/전체. 즉시 종료는 별도 케이스로 기록한다.
4. 가능한 계정 전환/새 진입에서 이전 선택이 보이지 않는지 확인한다. 같은 WebView 생존 중 전환은 별도 미확정 사례다.
5. 결과→재료→홈→종료의 토스 back/Android back, home/닫기/더보기, 등록 스킴 진입을 확인한다.
6. 핀치·두 번 탭 확대, 카테고리/칩/슬라이더/CTA/세로 스크롤을 확인한다.
7. 재료 콘텐츠가 긴/짧은 환경과 회전/글자 크기 변화에서 배너 노출/해제·safe area·가로 넘침을 확인한다. 정상 테스트 광고와 no-fill/실패는 가능한 환경에서만 실행하고 불가능하면 미실행 이유를 적는다.
8. 플랫폼 UI·콘솔 메타데이터·UX/조건부 기능을 대조하고, 반응시간은 타임스탬프가 있는 영상 등 측정 근거로 기록한다. 단순 체감으로2초 기준을 통과시키지 않는다.

승인 후 라이브의 실제 광고 노출은 테스트 광고 QA와 별도이며 이 계획 실행만으로 출시하지 않는다.

## 검증 명령과 문서 점검

후속 제품 검증 명령: npm test / npm run lint / npm run build. 실패가 생기면 원인·조건을 기록하고 완료로 표시하지 않는다. 이번 문서 전용 변경에서는 제품 테스트를 재실행하지 않으며 상대 링크·코드 경로·ID 대응·상태 및 git diff --check를 검사한다.

문서 검증 결과와 변경 파일은 Git Change Record의 Files→Change→Before→After→Verification 순서로 기록한다. 별도 D:\Codex 로그는 사용자 선택으로 생략한다.
