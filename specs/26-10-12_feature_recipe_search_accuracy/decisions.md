# 결정·미확정 사항

## 해석한 전제 (확인 필요)

사용자 요청은 "레시피 검색 정확도 상승"이다. 이 앱에는 텍스트 검색이 없어 **재료 기반 추천의 정확도**로 해석했다. 레시피 이름 검색을 새로 만드는 일이라면 범위가 크게 달라진다.

## 사용자 결정이 필요한 것

1. 범위 해석: 추천 정확도(제안) vs 이름 텍스트 검색 추가.
2. 선택 방식: B(상위 구간 무작위, 제안) / A(가중 무작위) / C(정렬 순서대로).
3. 다양성 허용선: 다시 뽑기로 서로 다른 메뉴가 나오는 정도를 얼마까지 낮출 수 있는지(제안: 후보가 5개 이상이면 연속 3회 뽑기에서 중복 없이 3개 노출 가능).
4. 점수 동점 처리: 매칭률만 쓸지, 난이도도 반영할지(제안: 매칭률만).
5. 이름이 같은 레시피 20개: 그대로 둘지, 하나만 노출할지, 구분 표기를 붙일지(제안: 먼저 표본을 보고 결정).
6. 평가 세트 조합: 이 문서의 일상 조합 10개로 충분한지, 추가할 실제 사용 조합이 있는지.

## 미확인

- 실제 사용자 재료 조합과 클릭·재뽑기 로그는 없다. 효과는 합성 지표로만 말한다.
- 이름 중복 20개와 원문 불일치 의심 항목의 실제 영향.

## 결정 처리 (2026-10-12: 제안대로 진행)

1. 범위: 재료 기반 추천 정확도로 진행(이름 텍스트 검색은 하지 않음).
2. 선택 방식: B(점수 상위 구간 무작위). 풀 크기는 max(5, 후보의 25%).
3. 다양성: 후보 5개 이상이면 연속 3회 다시 뽑기에서 서로 다른 메뉴 3개를 만날 수 있음(테스트로 고정).
4. 동점: 매칭률만 사용(난이도 미사용).
5. 이름 중복 20그룹(40개): 표본 확인 결과 모두 재료·조리 단계가 다른 별개 레시피(13그룹은 식약처↔EPIS). 삭제·병합하지 않고 유지하되 다시 뽑기에서 직전과 같은 이름은 제외(대안이 없으면 id 규칙으로 대체).
6. 평가 세트: 일상 조합 10개 유지.

## RSA-04 별칭 감사 결과

별칭 표 전체를 읽고 오연결 위험 항목을 뽑아 실제 레시피 영향(원문에 해당 이름이 있는 레시피 수)을 확인했다.

| 별칭 → 연결 | 영향 레시피 | 판단 |
| --- | --- | --- |
| 배추·알배추·배추잎 → 양배추 | 27+5+2 | **오류 확인·수정**: 별도 선택 재료 배추(napa_cabbage) 추가, 양배추와 분리 |
| 얼갈이 배추·절인 배추 | 각 1 | 다른 재료이므로 계속 미지원으로 보존(이름 단위 비교로 오인 방지) |
| 오이피클·다진오이피클 → 오이 | 2 | 레시피 1개만 연결, 영향 작아 보존(기록만) |
| 크림 → 생크림, 요리당 → 설탕 | 각 1 | 영향 작아 보존(기록만) |
| 순두부·연두부 → 두부 | 3·4 | 형태 차이이나 일상 선택에서 두부로 대체 가능해 허용 |
| 숙주·콩나물 → 콩나물·숙주 | 13 | 화면 칩이 하나로 묶여 있어 의도된 통합 |
| 발사믹·감·허브식초 → 식초, 파마산·모짜렐라치즈 → 치즈, 홀토마토 → 토마토 | 소수 | 같은 계열로 허용 |

배추는 생성 데이터에 양배추 id로 이미 들어 있어 합성 단계(recipes.ts)에서 원문 이름 기준으로 id를 바로잡는다. 원문에 배추와 양배추가 함께 있으면 둘 다 요구한다. 생성 파일과 원문 분량·조리 순서는 수정하지 않았다.

## 남은 위험·미확인

- 별칭 감사는 위험 후보 표본 방식이며 전체 매핑 정확도를 보증하지 않는다.
- 나머지 원문 불일치 의심 항목 추가 대조(기존 RSC-12 잔여)는 이번에 하지 않았다.
- 실제 사용자 조합·클릭 로그는 없다.
