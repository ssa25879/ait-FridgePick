# 검증

문서 준비, 코드 구현, 자동 검증, 브라우저 모의 검증, 토스 실기기 검증, 콘솔 검수·출시를 구분한다. 수행하지 않은 항목은 완료로 표시하지 않는다.

## 이번 준비에서 확인한 것

| 항목 | 상태 | 근거 |
| --- | --- | --- |
| 현재 규칙에서 준비 완료가 거의 나오지 않음 | 확인(합성 데이터) | 2026-10-20 임시 측정, 재료 5/8/12/16개에서 0개인 비율 98/99/95/89% |
| 기본 양념 9개 가정 시 예측 | 확인(합성 데이터) | 2026-10-20 재측정: 재료 5/8/12/16개에서 평균 1.0/1.7/2.8/4.6개, 0개인 비율 30/12/4/1% (참고: 33개 전체는 1.2/2.2/3.9/6.9개) |
| 준비 가능한 레시피 수 | 확인 | 1,359개 중 215개(미지원 재료·원문 안내 없음), 그중 필수 양념이 기본 9개 안에 있는 것은 110개 |
| 임시 측정 파일 | 삭제 | 저장소에 남기지 않음 |

측정의 한계: 냉장고는 레시피 사용 빈도에 비례해 무작위로 만든 합성이며 실제 사용자 선택이 아니다. 양념은 선택 풀에서 제외했다. 이 측정은 "현재 규칙 / 기본 양념 9개 / 33개 전체"를 같은 냉장고로 비교했다.

## 구현 결과 (2026-10-20)

- 추가: `src/utils/assumedSeasonings.ts`(+테스트 4개), `recommendRecipe.ts`에 `assumedSeasoningIds` 분리, `ResultPage` "양념 확인" 구역과 상태 문구, `IngredientPage` 안내 문구(+테스트 2개). 신규·갱신 테스트는 `recommendRecipe.test.ts`(7개 추가), `ResultPage.test.tsx`(5개 추가) 등.
- 갱신한 기존 테스트(의미가 바뀐 기대값만): `recommendRecipe.test.ts` 2개(양념이 부족 목록에서 가정 목록으로 이동), `recipes.test.ts` 1개(fsk_834: 달걀은 부족, 소금은 가정), `ResultPage.catalog.test.tsx`(소금은 "양념 확인"에 표시), `App.loading.test.tsx`(모의 후보에 새 필드 추가, 부족 재료 예시를 소금 대신 양파로), 그 외 `RecipeMatch` 리터럴에 `assumedSeasoningIds: []` 추가.
- 자동 검증: `tsc -b` 오류 없음, `npm test` 25파일 290개 통과(기존 272 + 18), `npm run test:scripts` 10개 통과, lint 기존 경고 1개만, `npm run build` 성공(deploymentId 01a157d1-4ade-72d0-a244-db2ef18fbc59).
- TEST-02(후보 불변): 합성 냉장고 600개(재료 5/8/12/16개 × 150)에서 변경 전 코드와 새 코드의 후보 목록·`matchRate`가 **모두 같음**(불일치 0).
- TEST-08(전후 비교, 실제 코드로 재측정, 합성 냉장고): 평균 준비 완료 / 0개인 비율 — 5개 0.0(99%) → 1.0(33%), 8개 0.0(99%) → 1.8(9%), 12개 0.0(96%) → 2.9(4%), 16개 0.1(89%) → 4.3(1%). 예측(1.0/1.7/2.8/4.6)과 비슷하다. 임시 측정 파일은 삭제했다.
- TEST-09(320×640 개발 서버): 재료 선택 화면 안내 문구 15px·가로 넘침 없음. 실제 카탈로그에서 재료 8개(김치·밥·달걀·양파·돼지고기·두부·당근·버섯)로 "바로 만들 수 있는 메뉴 1개"가 나오고, 결과에 "기본 양념을 빼고 필요한 재료를 모두 선택했어요"와 "양념 확인: 식용유"가 표시됐다.
- 미수행: 광고와의 비겹침, 테스트 번들 업로드, 토스 실기기 확인(TEST-10), 출시.
- 한계: 효과는 합성 냉장고 기준이며 실제 사용자 선택이 아니다. 준비 완료가 가능한 레시피 자체가 215개뿐이라(미지원 재료·원문 안내 없음) 평균 개수의 상한이 낮다. 그 한계는 미지원 재료 매핑으로만 풀린다.
