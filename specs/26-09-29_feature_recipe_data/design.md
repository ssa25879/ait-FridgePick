# 디자인: 레시피 데이터

## 설계 기준

기존 재료 카탈로그와 같은 로컬 TypeScript 상수 방식을 유지한다. 외부 저장소나 새 런타임 의존성 없이 `Recipe` 타입, 데이터, 무결성 테스트를 각각 책임에 맞게 둔다.

## 데이터 계약

- `src/types/recipe.ts`에 `RecipeDifficulty`와 `Recipe`를 둔다.
- 난이도는 프로젝트 기획서와 같이 `easy | normal`이다.
- 필수·선택 재료 필드는 현재 `Ingredient.id`와 같은 문자열 ID를 사용한다.
- 조리 단계는 짧은 한국어 문장 배열이다.

## 카탈로그

- `src/data/recipes.ts`의 `RECIPES`가 20개 메뉴를 내보낸다.
- 1차 카탈로그는 볶음밥, 볶음, 찌개, 계란 요리, 파스타를 포함한 간단식 위주로 구성한다.
- 각 메뉴는 고유한 소문자 ASCII snake_case ID를 가진다.
- 필수 재료는 3~6개이며 선택 재료가 있으면 `optionalIngredients`에 기록한다.
- 조리 단계는 3~5개다. 기본 조리 도구와 물처럼 재료 카탈로그의 선택 항목이 아닌 일반 조리 전제는 재료 ID에 추가하지 않는다.

## 무결성 검증

`src/data/recipes.test.ts`에서 `INGREDIENTS`의 ID 집합과 `RECIPES`를 비교한다. 다음 조건을 검사한다.

1. 카탈로그가 20~30개이고 레시피 ID가 고유하다.
2. 레시피 이름과 ID가 비어 있지 않다.
3. 필수 재료가 3~6개이며 ID가 유효하고 중복되지 않는다.
4. 선택 재료 ID가 유효하며 필수 재료와 겹치지 않는다.
5. 조리 단계가 3~5개의 비어 있지 않은 문자열이다.
6. 난이도가 `easy` 또는 `normal`이다.

데이터는 이후 추천 로직에서 직접 import해 사용한다. 이번 단계에서는 UI와 계산 함수를 만들지 않는다.
