## 사용자 결정이 필요한 항목

세션 1 시작 전에 1·2번과 8번을, 나머지는 게이트 G1 전에 정한다.

| 번호 | 결정 | 선택지 | 제안 |
| --- | --- | --- | --- |
| 1 | 정리 방식 | A 제자리 재작성 / **B 새 저장소** / C 재작성 없이 private만 | **B**. 기존 저장소를 건드리지 않아 가장 안전하다. 부담이 크다고 보면 C로 낮출 수 있다 |
| 2 | 현재 저장소 처분 | **private + 이름 변경(보관)** / 삭제 | private 보관이 먼저, 삭제는 세션 3의 삭제 게이트 이후. 삭제는 되돌릴 수 없다 |
| 3 | 새 저장소 이름 | 기존 이름 유지(옛 저장소를 `ait-FridgePick-archive`로 변경) / 새 이름 | 기존 이름 유지. URL·문서 변경이 최소다 |
| 4 | 새 저장소 공개 범위 | private 유지 / public | private 유지(세션 3 이후 재검토). public 전환 전에는 전체 이력을 다시 검색한다 |
| 5 | 광고 그룹 교체 | 유지 / 교체 | 먼저 이력 정리와 private 전환을 하고, 콘솔 지면의 어뷰징 수준이 `NONE`이면 유지. 이상 징후가 있을 때 교체 |
| 6 | 로컬 전용 브랜치 3개와 스태시 1개 | 새 저장소에 올림 / 백업에만 보관 | 백업에만 보관하고 필요하면 나중에 정리본에서 가져온다. codex 작업 트리 2곳은 옛 폴더에 그대로 둔다 |
| 7 | 도구 설치 | `pip install git-filter-repo` 승인 / `filter-branch` 대안 | 설치 승인(속도·정확성·대응표). 거부하면 대안으로 연습한다 |
| 8 | 백업 외부 보관 위치 | 다른 디스크 / 클라우드 / USB | 사용자가 정한다. 동일 디스크만으로는 부족하다 |
| 9 | 문서의 옛 해시 | 새 해시로 전부 치환 / 그대로 두고 대응표 위치만 기록 | 대응표 위치만 기록하는 쪽이 안전하다(문서 의미 변경 없음). 치환은 기계적이라 위험이 낮아 원하면 가능하다 |

## 설계에서 정한 것

- 세션 1·2에서는 삭제·덮어쓰기·강제 푸시를 하지 않는다(방식 B).
- GitHub 계정·저장소 설정은 사용자가 직접 한다.
- 비밀값은 저장소 밖 파일에만 둔다. 문서에는 `<AD_GROUP_ID>`로 쓴다.
- 이력 정리 동안 앱 기능 작업과 원격 푸시를 동결한다.

## 확인하지 못한 사실

| 항목 | 이유 | 확인 방법 |
| --- | --- | --- |
| `master` 등의 브랜치 보호 규칙 | 계정 설정이라 확인 불가 | 사용자가 Settings → Branches에서 확인 (방식 A에서만 중요) |
| private 저장소에서 CI(Actions)가 동작하는지, 사용 한도 | 계정 설정 | 세션 0·2에서 첫 푸시 후 확인 |
| GitHub에서 저장소 삭제 후 복구 가능 여부와 기간 | 확인하지 않음 | 삭제 전에 GitHub 공식 문서 확인 |
| 이미 외부에 복제·캐시된 사본 존재 여부 | 알 수 없음. 포크 0개, 별 0개만 확인 | 확인 불가, 광고 그룹 교체로 대응 |
| 새 저장소 푸시 시 용량·시간 | 저장소 크기 약 2.2MB라 문제 없을 것으로 추정 | 세션 2 |
| Python 환경에서 `git-filter-repo` 설치 가능 여부 | Python 3.12는 확인했으나 설치는 안 함 | 세션 1 S1-4 |
