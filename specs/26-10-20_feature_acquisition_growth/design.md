# 설계

## 원인 가설 (검증 전)

1. **발견 경로 부족**: 키워드가 일반 명사 6개뿐이고 부제·설명이 사용자 표현("오늘 뭐 먹지", "냉파")과 거리가 있다. 검증: 콘솔 검색 유입 키워드 수치(현재 노출 조회 도구 없음)·키워드 교체 후 검색 유입 변화.
2. **노출 정책 변화**: 10-22 이후 출시 미니앱은 검색·공유 링크 외 노출이 제한된다. 지표 없는 앱은 추천 대상이 되기 어렵다.
3. **재방문 사유 부재**: 한 번 메뉴를 정하면 끝나는 도구형 앱이다. 현재 D1 0%는 표본이 작아 결론이 아니며, 사유 부재는 가설이다.
4. **지표 오염 가능성**: 활성일이 소유자의 기기 QA·검수 확인 날짜와 겹치지만(Task.md), 사용자가 기록된 방문은 전부 본인이 아니라고 알렸다. 이에 따라 약 5명을 외부 사용자로 본다. 콘솔로 확인할 수 없는 진술이므로 이후 구현에서 본인 QA 방문이 섞이지 않게 이벤트 로그에 구분 수단을 둘지 검토한다.
5. **재실행 시 선택 초기화**: 현재 정책은 실행 중에만 선택을 유지하고 재실행하면 초기화한다(사용자 결정, Task.md 10-06). 콘솔 상세 설명과 일치하므로 불일치 문제는 아니다. 매번 처음부터 고르는 경험이 재방문 동기를 낮출 수 있다는 점은 가설로만 남기고 정책 변경은 이번 범위가 아니다.

## 퍼널과 이벤트

단계: `entry` → `ingredient_select_start` → `result_view` → `reroll` → `share_tap`.

- SDK(`@apps-in-toss/web-framework` 3.2.0)의 `eventLog`는 deprecated이며 `Analytics.log({ log_name, log_type, params })`를 쓴다(타입 정의·공식 문서 확인). `anonymous_key`가 params에 자동 포함되고 미지원 버전에서는 조용히 무시된다.
- 구현: `src/analytics/funnelEvents.ts`의 `logFunnelEvent`. 이벤트별 허용 params를 타입으로 제한해 재료 ID·이름을 넣을 수 없게 했다. `log_type`은 `app_entry`·`result_view`·`result_empty`=`screen`, `ingredient_select_start`·`reroll`=`click`으로 정했다. 콘솔 핵심 지표가 어떤 `log_type`을 매칭하는지는 공식 문서에 명시가 없어 미확인이다.
- 공식 문서상 클릭 이벤트는 라이브 환경에서만 수집되고, 샌드박스·QR 테스트에서는 쌓이지 않으며, 데이터는 출시 다음 날부터 콘솔에 보인다. 따라서 콘솔 확인은 출시 후에만 가능하다.
- 이벤트에는 재료 목록 같은 선택 내용을 넣지 않는다. 개수 같은 비식별 값만 쓴다(개인정보·과도 수집 방지).
- 기록 실패가 화면 흐름을 막지 않도록 호출은 실패를 삼킨다(사용자 상태 저장의 실패 격리 방식과 동일한 원칙).
- 콘솔 `핵심 지표` 메뉴에서 활성 지표(앱당 1개)와 전환 지표(최대 3개, 대표 1개)를 이벤트 OR 조합으로 설정한다. 변경은 다음 날부터 적용된다. 전환 지표 후보는 `result_view`(대표), 보조로 `reroll`. 활성 지표 후보는 `app_entry`가 아니라 재방문 의미가 있는 `result_view`로 시작하되 결정은 콘솔 입력 시점에 한다.
- 이전 문장: 전환 지표 후보는 `result_view`. "재료를 골라 결과를 본 사용자 비율"이 이 앱의 핵심 가치와 직접 연결된다.

## 공유

- `getTossShareLink("intoss://ait-fridgepick", ogImageUrl)`로 링크를 만들고 `share({ message })`로 메시지 창을 연다. 딥링크는 현재 서비스 링크(`intoss://ait-fridgepick`)를 쓴다.
- 메시지 예: `오늘 저녁은 {메뉴명}! 토스에서 냉털픽으로 정했어요`. 메뉴명이 외부에 나가므로 사용자가 공유 버튼을 누를 때만 사용한다.
- OG 이미지는 https 절대 URL이 필요하다. 번들 안 정적 자산의 외부 접근 가능 여부는 구현 전에 확인한다(미확인). 불가하면 이미지 없는 링크로 시작한다.
- 받는 사람의 도착 화면은 기존 홈이다. 공유 받은 사람이 바로 같은 메뉴를 보는 기능은 범위 밖이다.

## 메타데이터 초안 (콘솔 변경은 별도 승인)

- 부제 후보(16자·15자): "남은 재료로 오늘 메뉴 정하기", "냉장고 속 재료로 메뉴 추천". 현재 "냉장고 재료로 오늘 메뉴 찾기"(16자).
- 키워드는 현재 6개. 허용 개수는 콘솔에서 확인한다(미확인). 후보: 레시피, 냉장고파먹기, 냉파, 오늘뭐먹지, 자취요리, 메뉴추천, 남은재료, 간단요리. 실제 검색량 데이터는 없으므로 후보일 뿐이다.
- 상세 설명은 가치(재료만 고르면 메뉴 하나를 정해줌)를 먼저, 기능 세부를 뒤에 쓴다. 현재 문장은 내부 동작 설명이 앞서고 마지막이 "초기화됩니다"라는 부정적 안내로 끝난다. 사실과 맞는지 확인한 뒤 수정한다.

## 재방문 장치 (후순위)

- 알림: 첫 진입에 요청하지 않는다. 결과를 본 뒤 "내일도 메뉴 고르기 알려드릴까요?" 같은 선택형으로만 제안한다. 스마트 발송은 서버 없이 콘솔에서 일회성·정기 발송이 가능하나 알림 동의문과 문구 검수(영업일 2~3일)가 필요하다. 광고성/기능성 구분과 비용은 구현 전 확인한다.
- 리뷰: `requestReview`를 결과 확인 후 한정된 조건에서만 호출한다.

## 프로모션

토스 포인트 프로모션은 사업자 등록·약관 동의·비즈월렛 충전(최소 5만 원)이 필요하다. 사용자가 사업자 등록을 보류했으므로 이번 범위에서는 구현하지 않고 선결 조건만 기록한다. 또한 기준선이 약 5명인 상태에서 예산을 쓰는 것은 효과를 판단하기 어렵다.
