# 설계

## 현재 구조 (코드 기준)

- 레시피 원본(`publicRecipes.ts`·`episRecipes.ts`)은 생성 결과이며 레시피마다 `requiredIngredients`(지원하는 재료 ID)와 `unmappedRequiredIngredients`(지원하지 않는 이름)를 가진다. 직접 고치지 않는다.
- `src/data/recipes.ts`의 `applyCurrentIngredientMappings`가 **실행 시점에** `unmappedRequiredIngredients`를 `mapRecipeIngredientName`으로 다시 매핑한다. 그래서 별칭을 추가하면 생성기를 다시 돌리지 않아도 반영된다.
- 이름 → 재료 ID: `src/data/recipeCatalog.ts`의 `INGREDIENT_ALIASES`. 선택 가능한 재료 목록: `src/data/ingredients.ts`.
- 레시피 단위 보정의 선례: `recipes.ts`의 `correctNapaCabbage`(원문 이름으로 배추를 양배추와 분리). 모호한 이름의 처리에 같은 방식을 쓴다.
- 준비 완료·후보 계산(`recommendRecipe.ts`, `recipeReadiness.ts`)은 바꾸지 않는다.

## 처리 방식 5가지

| 방식 | 의미 | 위험 | 재료 칩 증가 |
| --- | --- | --- | --- |
| A. 별칭 | 이미 있는 선택 재료와 뜻이 같은 이름을 `INGREDIENT_ALIASES`에 추가 | 의미가 다르면 오매핑(배추 사례) | 없음 |
| B. 새 선택 재료 | 자주 쓰이는데 선택 목록에 없는 재료를 추가 | 칩 수 증가로 화면이 길어짐 | 있음 |
| C. 새 양념류 재료 | 소스·조미료를 선택 재료로 추가(양념 카테고리) | 칩 수 증가. 가정 대상(기본 9개)에는 넣지 않음 | 있음 |
| D. 육수류 | 다른 재료에서 만드는 준비물(육수·닭육수·다시물·쌀뜨물·물전분) | 보유 가정이면 "바로 만들 수 있다"를 과장할 수 있음 | 결정에 따라 |
| E. 모호 | 하나로 단정할 수 없는 이름(호박·기름) | 일괄 매핑하면 오매핑 | 없음(레시피별 보정) |

## 상위 이름 분류표 (2026-10-20, 고유 상위 45개)

빈도는 해당 이름이 필수 재료에 들어 있는 레시피 수다. 아래 분류는 **제안**이며, 각 항목은 구현 직전에 원문 사례로 다시 확인한다(UIM-02). 빈도 순서 상위 45개까지만 정리했고 그 아래는 같은 절차로 이어 간다.

| 방식 | 이름(빈도) | 근거·메모 |
| --- | --- | --- |
| A 별칭 | 통마늘(8), 배춧잎(8) | 마늘·배추(napa_cabbage)의 형태 표기. 배추는 양배추와 이미 분리됨 |
| A 별칭 | 달걀노른자(7), 계란노른자(9), 달걀흰자(7) | 달걀(egg)에서 나오는 부위. 부위만 따로 보유할 수는 없으므로 달걀로 묶는 것이 합리적이나 결정 3번에서 확인한다 |
| B 새 선택 재료 | 현미(12), 굴(10), 옥수수(8), 미역(8), 마(9), 아보카도(8), 유부(9), 어묵(9), 만두피(8), 게맛살(8), 메추리알(8), 꽃게(8), 은행(8), 견과류(9), 갓(9), 청포묵(7), 라이스페이퍼(9), 두유(9), 참외(7), 함초(8) | 20개. 카테고리·표기는 아래 표 참고. 마는 산마인지 원문 확인 필요 |
| C 새 양념류 | 까나리액젓(9), 멸치액젓(8), 고추기름(10), 와사비(9), 토마토페이스트(8), 계피가루(7), 콩가루(7), 레드와인(10), 화이트와인(9), 오렌지주스(7), 배즙(9), 마른고추(8), 실고추(8) | 13개. 마른고추·실고추는 기존 고추(`chili_pepper`)와의 구분을 결정 4번에서 확인 |
| D 육수류 | 육수(53), 닭육수(17), 다시물(8), 쌀뜨물(9), 물전분(9) | 사용자 결정 1번 필요. 결정 전에는 미지원 유지 |
| E 모호 | 호박(21), 기름(32) | 호박은 애호박·단호박·늙은호박 가능. 기름은 식용유·튀김기름·참기름 등 가능. 레시피별 확인 |

주의: 위 "근거"는 원문 샘플 확인에 기반한 임시 판단이다. 샘플은 이름이 포함된 줄을 단순 검색한 것이어서(예: "기름"이 "참기름" 줄에 포함됨) 정확한 의미 구분은 구현 시 레시피별 확인이 필요하다.

### B류 카테고리 초안 (결정 필요)

앱의 카테고리는 채소·과일 / 단백질 / 계란·유제품 / 탄수화물 / 양념 5개다.

| 카테고리 | 후보 |
| --- | --- |
| 채소·과일 | 옥수수, 마, 아보카도, 갓, 참외, 은행, 미역, 함초 |
| 단백질 | 굴, 꽃게, 어묵, 게맛살, 유부, 견과류 |
| 계란·유제품 | 메추리알, 두유 |
| 탄수화물 | 현미, 만두피, 라이스페이퍼, 청포묵 |

## 레시피별 보정 (E류)

`src/data/recipeIngredientOverrides.ts`(신규): `{ 레시피ID: { 원문 이름: 재료 ID } }` 형태. `recipes.ts`의 매핑 단계에서 별칭보다 먼저 적용한다. 각 항목은 원문 줄을 근거로 사람이 확인한 것만 넣고, 확인 안 된 레시피는 미지원으로 둔다. 항목 수가 53개 수준(호박 21 + 기름 32)이라 수작업 확인이 가능하다.

## 배치 순서

비용 대비 효과와 위험을 기준으로 배치를 나눈다. 각 배치는 독립적으로 병합·검증할 수 있다.

1. **1차(칩 증가 없음)**: A 별칭 + E 레시피별 보정. 위험이 낮다. 측정: 215 → 231개(임시 측정, 호박·기름은 일괄 처리 가정이라 실제는 확인된 레시피 수만큼만 증가한다).
2. **2차(칩 20개)**: B류. 사용자 승인 필요(결정 2번).
3. **3차(칩 13개)**: C류. 사용자 승인 필요.
4. **4차**: D류. 결정 1번 이후.

임시 측정(분류표의 45개 이름을 모두 해소했을 때 준비 가능 레시피 수): 215 → A 223 → A+B 252 → A+B+C 280 → A+B+C+D 302 → +E 310. 이름 하나당 평균 2개 안팎의 증가다.

## 실패 유형 구분

- 매핑 누락(별칭으로 해결), 카탈로그 부재(새 선택 재료), 의미 모호(레시피별 보정), 파생 준비물(결정 필요)은 원인이 달라 처리도 다르다.
- 오매핑은 사용자에게 "다 있다"고 잘못 안내하므로 가장 큰 위험이다. 의심되면 매핑하지 않고 미지원으로 남긴다(안전한 쪽으로 실패).

## 디자인 패턴

필요하지 않다. 데이터 표 확장과 레시피별 보정 표로 충분하다.
