# 설계

## 현재 흐름과 개선 지점

1. `App.tsx`가 `getRecipeCandidates`로 후보를 계산한다(주재료 매칭률 ≥ 60%, 난이도 필터).
2. 준비 완료(`isRecipeReady`)가 있으면 그 그룹, 없으면 전체 후보 그룹에서 `pickRecipeCandidate`가 **균등 무작위**로 하나를 고른다.
3. 다시 뽑기·그룹 전환도 같은 함수를 쓰며 직전 메뉴만 제외한다.

개선 지점은 2~3번의 선택 방식(RSA-02)이고, 후보 계산 규칙은 바꾸지 않는다.

## 선택 방식 후보와 비용

| 방식 | 설명 | 장점 | 비용·위험 |
| --- | --- | --- | --- |
| A. 가중 무작위 | 점수(부족 수가 적을수록 높음)에 비례해 확률을 준다 | 다양성 유지, 구현이 작음 | 가중치 튜닝이 필요 |
| B. 상위 구간 무작위 | 점수 순 정렬 후 상위 N개 또는 상위 구간에서 균등 무작위 | 이해하기 쉬움, 결과가 안정적 | N이 작으면 반복 노출 |
| C. 정렬 순서대로 노출 | 다시 뽑기 때 다음 순위를 보여줌 | 가장 정확, 예측 가능 | 무작위성이 사라져 "뽑기" 경험이 변함 |

권장 출발점은 B(점수 상위 구간 무작위, 구간이 소진되면 다음 구간)다. 전략 패턴 같은 별도 추상화는 도입하지 않고 `pickRecipeCandidate`에 점수 함수와 구간 계산을 순수 함수로 추가한다. 무작위 소스(`random`)는 지금처럼 주입해 결정적으로 테스트한다.

## 점수 정의(초안)

- 부족 재료 수 = 부족 필수 재료 수 + 부족 미지원 필수 재료 수(낮을수록 좋음).
- 동점이면 주재료 매칭률이 높은 쪽. 난이도·조리 단계 수는 사용하지 않는다(미확정).
- 검토 안내가 있는 레시피는 준비 완료에서 제외되는 기존 규칙을 유지하고, 점수와 별개로 취급한다.

## 실패 유형 구분

- 선택 불공정: 점수 계산이 후보 집합을 바꾸면 안 된다(후보는 기존 함수 그대로).
- 매핑 오류: 잘못된 재료 연결 → RSA-04 감사로 수정.
- 원문 불일치: 이미 있는 검토 안내 메커니즘 사용(RSA-05).
- 표시 오해: 매칭률 문구 → RSA-06.

## 제약

- 추천 모듈은 지연 로딩 청크다(`loadRecommendationModule`). 새 코드도 이 청크 안에 둔다.
- 상태 저장 정책(새 실행 시 초기화)과 사용자 선택·필터 구조는 변경하지 않는다.
- 평가 세트는 합성이다. 실제 사용자 로그가 없으므로 효과를 확정하지 않는다.
